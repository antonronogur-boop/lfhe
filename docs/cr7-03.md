## 1. Problem

The first measured REPLAY pilot cycle could not be run. The chain claims → events → relevance → assessment → human review
→ approved assessment → report candidate was not operable on DEV:

* no web interface existed for the Phase 3–4 human decisions (`create_event`, `review_event_version`, `set_event_state`,
  `decide_relevance`, `promote_event_version`, `dispose_challenge_flag`, `review_assessment`,
  `modify_and_approve_assessment`) — accepted at CG4 as a non-blocking item (L-32, "Phase 4 review UI");
* nothing could enqueue the existing worker jobs `ANALYSE_LINEAGE` (M04), `BUILD_EVENTS` (M05), `ASSESS_RELEVANCE` (M06),
  `ASSESS_EVENT` (M07): only the test harness did. `EXTRACT_CLAIMS` (M02) was enqueued only by a worker flag.

## 2. Impact

Without approved assessments the report candidate pool stays empty, so no pilot cycle can reach a terminal state
(RELEASED / *_REJECTED). Creating a report and cycle anyway would start the cycle clock (`started_at`) and invalidate the
turnaround measurement. Recorded as UX finding: area `EVENT_ASSESSMENT`, severity `BLOCKING`, class `USABILITY_DEFECT`,
title "No UI / request path from claims to approved assessment".

## 3. Root cause

Phases 3–4 delivered the database functions, worker handlers and ingestion with automated tests, but (by their accepted
scope) no operator entry point. The job types were defined (`processing_jobs_job_type_check`), the handlers exist in
`lfhe_orchestrator.worker.make_handlers`, but no production enqueuer existed for M04–M07.

## 4. Scope (what CR7-03 adds)

**Database (migration 4300, additive):**

* `lfhe.request_workflow_job(job_type, params, reason)` — HUMAN_ONLY (SECURITY DEFINER, fixed `search_path`). Allowed job
  types and permissions: `EXTRACT_CLAIMS` (CLAIM_REVIEW), `ANALYSE_LINEAGE` (CLAIM_REVIEW), `BUILD_EVENTS` (EVENT_ACTION),
  `ASSESS_RELEVANCE` (ASSESSMENT_REVIEW), `ASSESS_EVENT` (ASSESSMENT_REVIEW), `CHALLENGE_ASSESSMENT` (ASSESSMENT_REVIEW) — the
  permissions of the corresponding human steps. Report jobs keep their existing human paths (`freeze_report_selection`,
  `request_report_qa`, security approval).
* `lfhe.request_pending_claim_extractions(limit, reason)` — HUMAN_ONLY bulk M02 request, same selection and idempotency key
  as the closed worker function `enqueue_pending_claim_extractions`.
* `lfhe.workflow_job_requests` — append-only (UPDATE / DELETE / TRUNCATE blocked), RLS (CLAIM_READ), one row per human
  request: actor, reason, exact object, mode / cutoff, payload, outcome, job id. Audit event `WORKFLOW_JOB_REQUESTED`.
* `lfhe.workflow_job_request_status` — read view (request + current job status: QUEUED / RUNNING / SUCCEEDED /
  NEEDS_HUMAN_REVIEW / FAILED / SKIPPED, attempts, last error).

**Web (`apps/web`):** application shell with role-aware navigation; dashboard; claims (needs-review / all / article
intake, detail with original-language span, provenance, history); events (list, manual creation, detail with claims and
roles, contested evidence, review, state, relevance, promotion, M06 / M07 requests); assessments (queues, detail with
FACT / ASSUMPTION / ASSESSMENT separation, likelihood vs analytic confidence, M07 / M08 separation, challenge flag
dispositions, human review, modify-and-approve); pipeline jobs; decision queues for REVIEWER / SECURITY_REVIEWER /
RELEASE_AUTHORITY; reports and pilot restyled; pilot workspace summary; loading / error / empty / locked states.

**Tests:** `tests/integration/test_cr7_03_requests.py` (7), web unit tests, browser E2E
(`tests/e2e/test_pilot_path_e2e.py`, 2) with a local test-only stack.

## 5. Non-scope

No change to any Phase 1–6 table, function, trigger, view, prompt bundle, ingestion rule, QA rule, approval, security or
release semantics; no new role or permission; no change to the worker handlers, provider abstraction, CR7-01 / CR7-02,
model choice (`anthropic / claude-sonnet-5-5`, provider-fixed sampling) or cost / price records. No merge / split /
supersede UI (the existing functions stay available; M05 suggestions of that kind are shown read-only). No dependency
upgrade (Next.js 16.4.0 stays; DEV / localhost only).

## 6. Rules preserved

| Rule | How |
| --- | --- |
| Human-in-command | Requests need a human session; `service_role`, `lfhe_worker`, `anon` have no EXECUTE (tested). A request never approves, decides or changes analytical state; M05 / M04 output still ends in HUMAN_REVIEW. |
| M07 regardless of M06 is an audited override (Phase 4 §4.1) | `ASSESS_EVENT` requires an M06 result recommending assessment for the exact event version **or** an audited `PROMOTE` / `REQUEST_ASSESSMENT` decision (`promote_event_version`) first (`MANUAL_ASSESSMENT_REQUEST_REQUIRED`). |
| REPLAY / LIVE cutoff | Mode and cutoff are explicit; claims / event versions must be eligible under the closed `claim_cutoff_eligible` / `event_version_eligible`. The UI takes mode + cutoff from an existing report (server-side lookup) or LIVE now. |
| Idempotency, retries | Deterministic key per job type + exact object + mode + cutoff + prompt version (+ options). Repeat while QUEUED / RUNNING → `ALREADY_ACTIVE`; after completion → `ALREADY_COMPLETED` (no re-run); after a permanent `FAILED` (max_attempts exhausted under `fail_job`) → one new job `…:retry:n` (`REQUEUED_AFTER_FAILURE`). Concurrent requests are serialised (advisory lock). The M08 key equals the worker's automatic chain key: never a second challenge of one version. |
| Final confidence only by human approval | Unchanged (`review_assessment` / `modify_and_approve_assessment`); the UI shows AI-recommended and final confidence separately. |
| FACT / ASSUMPTION / ASSESSMENT, likelihood vs confidence | Displayed separately from the stored `epistemic_category`, `likelihood_term`, final confidence. |
| Provenance / audit | Every action is an existing audited HUMAN_ONLY function; requests are audited (`WORKFLOW_JOB_REQUESTED`) and append-only. |
| Release authority | Unchanged; the UI only exposes the existing Phase 6 functions; queues are read-only lists. |

## 7. Security impact

Two new HUMAN_ONLY functions, EXECUTE only for `authenticated` (no `anon`, `service_role`, `lfhe_worker`, evaluator,
registrar); internal helpers not executable by any API role. New table with RLS and no write privilege for any
application role; append-only triggers. The view exposes job status / last error (truncated to 500 characters) only to
CLAIM_READ holders. The web never holds a service key (`lib/env.ts` refuses it). The E2E stack is local and test-only
(per-run random JWT secret and passwords, never DEV).

## 8. Audit impact

New audit event type `WORKFLOW_JOB_REQUESTED` (object = processing job; payload: request id, job type, object, outcome,
key, mode, cutoff, reason). All other audit entries come from the unchanged functions.

## 11. Acceptance criteria

1. Analyst can start from claims in the UI (intake → M02; review). 2. Events can be created / built (M05) and handled
(review, state, edit). 3. M04 / M05 / M06 / M07 / M08 jobs can be requested by a human, idempotently, audited, with
visible status. 4. The unchanged worker processes them. 5–7. Assessment appears, human review is possible, an approved
version is created only by a human. 8. The report candidate pool picks it up. 9–16. Report, QA, warning
acknowledgement, content approval, security review, release decision, released PDF / manifest work from the UI.
17. Pilot timing / measurement unaffected. 18. Role boundaries hold. 19. Audit / provenance intact. 20. Browser E2E
proves the path. — All met in the local test stack (technical E2E). Not yet evidenced on DEV: merge, migration 4300, DEV
smoke, worker M02–M10, recording / disposition of the BLOCKING UX finding and the human P7-04 walkthrough (PO).
